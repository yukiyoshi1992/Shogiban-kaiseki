# 001生データ（学習データ（対局画像＋対局kif）3/001 ※画像が90度回転して入ってきている場合のパターン）認識誤り分析

2026-06-19セッションで作成。`001生データを100%にする`タスクのための調査記録。
目視確認はユーザー側で行う方針（Claudeの画像認識は信頼性が低いため）なので、
このドキュメントは「どの手の・どの画像の・どのマスが・正解は何で・モデルは何と読んだか」を
機械的に洗い出した一覧と、そこから読み取れる傾向のみを記録する。

## 調査方法

`train/src/audit_recognition.py`（本セッションで新規作成）を使用。
従来の`detect_move.py`は「直前の差分から合法手を探す」方式のため、1回失敗すると盤面が
凍結し、以降の差分が雪だるま式に増える（カスケード）。これでは「本当にその手で誤読したのか」
「過去の凍結状態のせいで誤読扱いになっているだけか」を区別できない。

`audit_recognition.py`はこれを避けるため、各画像を**KIFを再生して得た「その時点の正解局面」と
直接比較する**（カスケードなし、画像[i] vs KIF局面[i]の1:1比較）。これにより、各フレーム・各マスが
本当に正しく認識できているかを独立に判定できる。

```bash
python train/src/audit_recognition.py \
  --kif    ".../001 ※画像が90度回転して入ってきている場合のパターン/001.kif" \
  --images ".../001 ※画像が90度回転して入ってきている場合のパターン/" \
  --calib  "runtime/result/001raw_calib.json" \
  --model  "train/models/" \
  --out-pkl "runtime/result/audit_001raw.pkl"
```

## 結論1: キャリブレーションのズレが原因ではない（確定）

同じ79枚の写真に対し、**2つの完全に独立したキャリブレーション経路**で比較した。

- 経路A: `001 ※画像が90度回転して入ってきている場合のパターン/`の生画像 + 青三角検出(up→反時計90度回転) + 本セッションで手動作成した`runtime/result/001raw_calib.json`
- 経路B: 同じゲームの別収録写真`001_180fix/`（ファイル名は経路Aと同一79枚。別途180度補正済み）+ 回転なし + 既存の`train/src/対局v2_calib/001_calib.json`

結果は**完全に一致**（フレームごとの不一致マス数、マスごとの誤読パターンまで1件残らず同一）。
よってキャリブレーション/座標変換/回転方向のバグは排除でき、純粋にモデルの認識精度の問題と確定した。

## 結論2: 確信度(confidence)は誤読の手がかりにならない

| | 平均確信度 |
|---|---|
| 正解時 | 1.0000 (n=4243) |
| 誤読時 | 1.0000 (n=2156) |
| 誤読のうち確信度<0.9 | 0/2156 (0%) |
| 誤読のうち確信度>=0.99 | 2156/2156 (100%) |

モデルは誤読していても常に「確信度1.0」を返す。低確信度マスだけを機械的に検出して
人間に確認を求める、という運用は**この精度問題に対しては機能しない**。

## 全体傾向

- 全79フレーム中、完全一致（盤面81マス全て正解）は**3フレームのみ**。
- 延べ不一致マス数: 2156マス（全6399マス中）。
- 誤読は特定のマスに集中している（68マスで何らかの誤読が発生、しかしその中でも上位十数マスが
  圧倒的多数を占める）。ランダムな単発ミスではなく、**特定マスを継続的に間違え続けている**。

**重要な特徴**: 上記の各行は、座標(row,col)と(8-row,8-col)が必ずペアで現れ、駒の色（先手/後手）も
入れ替わった形で対応している（例: row2,col1の「sente_kin→sente_ou」と、点対称の位置row6,col7の
「gote_ou→gote_kin」は、色を入れ替えると同じ「kin/ou取り違え」パターン）。これは盤の中心に対して
点対称な位置で、先手側・後手側それぞれが同種の駒の見分けに失敗している、ということを意味する
（金/玉、銀/金、飛/空、など）。座標変換のバグでこうなる可能性も検討したが、結論1の通り2つの
独立した経路で同一結果のため、座標変換ではなく**モデル自体がこの部屋の写り方でこれらの駒の
組み合わせを見分けられていない**と考えられる。

## row2,col1（sente_kin/sente_ou周辺）の時系列の例

```
idx  6 IMG_20260616_150641.jpg: true=empty      pred=sente_kin  conf=1.0000
idx  7 IMG_20260616_150645.jpg: true=empty      pred=sente_kin  conf=1.0000
...(idx6-11: 正解はまだ空きマスだが、モデルは金が既にあると誤読)
idx 12-14: 一致（モデルの読みと正解が一致）
idx 15 IMG_20260616_150718.jpg: true=sente_kin  pred=empty      conf=1.0000
...(idx15以降: 正解は金が来ているが、モデルは空きマスと誤読し続ける)
```
→ 金が実際にこのマスへ来る前後で、モデルの誤読の方向が逆転している。
  単なる「このマスはいつも誤読する」という固定バイアスではなく、駒の出現/不在どちらの状態でも
  このマスの認識自体が不安定、という可能性がある。

## 次にユーザーに確認してほしいこと

1. `001raw_review_crops/`の切り出し画像を見て、上記の誤読が「本当にその駒が写っているように
   見えるか」「照明・ピント・反射などで紛らしい見え方になっていないか」を確認してほしい。
2. 特にrow2,col1 / row6,col7（金/玉の取り違え）のように、駒の種類自体が紛らわしいケースは
   この部屋の照明・カメラ位置に起因する可能性が高いと推測しているが、目視確認で裏付けたい。
3. もし「写真自体は明らかにこの駒だとわかる」のにモデルが外している場合は、学習データに
   この部屋の写真がほぼ含まれていない（cells/への寄与が3枚のみ）ことが原因と考えられ、
   再学習以外の対処は難しい可能性がある。逆に「写真自体が紛らわしい」場合は撮影条件の改善
   （照明・カメラアングル）も選択肢になる。
