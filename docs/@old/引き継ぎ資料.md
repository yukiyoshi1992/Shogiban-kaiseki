## 1. プロジェクト概要（企画）

スマートフォンのカメラで将棋盤を **1手ごとに1枚撮影** し、その画像列を解析して
**KIF形式の棋譜を自動生成** するツール。

### コアコンセプト
- 1手ごとの盤面画像を順番に解析し、前後の差分から「指し手」を推定する
- 駒の認識は CNN（MobileNetV2 転移学習）で各マスを29クラス分類
- 盤面の位置合わせは「赤丸マーカー」、盤の向き判定は「青三角マーカー」を使う

### 設計の根本思想（重要・ブレてはいけない軸）
1. **自動を基本、人手はフォールバック**
   プログラムが赤丸で自動キャリブレーション・青三角で向き自動判定する。
   失敗時のみ人間が手動でキャリブレーション・向き指定する。
2. **向きの違いは「画像回転」で吸収する（方式A）**
   学習データは「先手が左（横向き撮影）」を基準にしている。
   撮影画像の向きが違う場合は、**画像そのものを回転して横向きに直してから** 処理する。
   → 回転は画像に対して1回だけ。座標変換やグリッドラベル回転は一切しない（後述の重要教訓を参照）。

## 2. 確定仕様（要件・設計）

### 2-1. 座標系（厳守）
- `row=0`(上=9筋) 〜 `row=8`(下=1筋)
- `col=0`(左=先手側1段目) 〜 `col=8`(右=後手側)
- `square = (8 - col) * 9 + row`
- 学習データ基準の向き: **先手が左（横向き撮影）、先手駒は頭が右(▶)、後手駒は頭が左(◀)**

### 2-2. 青三角マーカーによる向き判定 → 画像回転方向
| 青三角の頂点方向 | 盤の向き | 画像回転（横向きに直すため） |
|---|---|---|
| right | 先手が左・横向き（基準） | 回転なし |
| up | 先手が手前・縦向き | 反時計90度 |
| down | 先手が奥・縦向き | 時計90度 |
| left | 先手が右・横向き | 180度 |

- 実際に起こりうるのは主に **right（横向き）と up（縦向き・先手手前）** の2つ。
- 「先手が奥(down)」「先手が右(left)」はほぼ発生しない（エッジケース）。
- スマホの仕様上、撮影向きが勝手に回転することがあるため、向き固定に頼らず
  青三角で判定 → 必要なら画像回転、という方式を採る。
  青三角は先手の向きが底辺、後手の向きが頂点になっている。

### 2-3. 本番運用フロー（run_realtime.py の0手目処理）
1. 監視フォルダに1枚以上が入る
2. 初期局面（0手目）の画像を青三角で向き判定 → 必要に応じて画像を回転（縦→横）
3. 初期局面（0手目）の画像を赤丸自動キャリブレーション
4. 標準初期配置と照合 `[y/n]`
   - `y`: OK、対局開始
   - `n`: 人が向きを手動指定（先手の方向がどっちに向いているか指定）。誤っていた場合は再度画像を回転。その後、人がキャリブレーションを実施（四隅をクリックして指定）。人の手で確実にあわせにいく。
5. 監視を続け、そのあと入ってくる画像を撮影順に分析する。各手も0手目で確定した向きに回転 → 回転後calib適用 → 認識・差分検出して分析。

### 2-4. 駒クラス（29クラス）
- empty
- 先手14種: sente_fu, sente_kyo, sente_kei, sente_gin, sente_kin, sente_kaku, sente_hi, sente_ou, sente_tokin, sente_nari_kyo, sente_nari_kei, sente_nari_gin, sente_uma, sente_ryu
- 後手14種: gote_ 同上

## 4. 重要な技術的教訓（ハマりどころ）

### 4-1. 三重回転バグ（解決済み・再発防止）
detect_move.py が以下の3つを重複適用してしまい認識が破綻していた:
1. 画像回転（rotate_image_for_direction）
2. calib座標回転（rotate_calib_for_direction）
3. グリッドラベル回転（apply_transforms）

**正解は「画像回転1回だけ」**。calibは回転後の画像で取得し、座標変換もグリッド変換もしない。
→ 検証で「回転後画像＋回転後画像で取得したcalib」だけで81マス完璧認識を確認済み。
**今後、向き対応で座標やグリッドを回転させる実装を足してはいけない。**

### 4-2. 駒の物理枚数制約（配置表作成時の必須チェック）
成り駒は元駒と札を共有する。同時に存在できる上限:
- 香系(香+杏): 4枚 / 桂系(桂+圭): 4枚 / 銀系(銀+全): 4枚 / 金: 4枚
- 角系(角+馬): 2枚 / 飛系(飛+龍): 2枚 / 王: 2枚 / 歩系(歩+と): 18枚
- **先手だけで見ると角・飛・玉・馬・龍は各1枚まで**（先手後手で1枚ずつ＝計2枚）。
配置表(駒配置表HTML)を作るときは必ずこの上限を検算すること。

### 4-3. キャリブずれの混入
キャリブレーションがずれた画像を学習データに入れると、歪んだマス画像で学習してしまう。
追加学習データ3の前は pattern8(3) のキャリブずれが混入していた（修正済み）。
新規データは check_labels.py で必ず目視確認してから学習する。

### 4-4. 文字コード・パスの注意
- ネットワークパスは bash 実行時 `//YukiYoshiNAS/...` 形式（`\\` はエラー）
- 画像の読み書きは日本語パス対応のため
  `cv2.imdecode(np.fromfile(...))` と `cv2.imencode(...)[1].tofile(...)` を使う
- 日本語ログは cp932 エンコードで出力されることがある
- 回転済み画像（`_rot.jpg`）を元画像フォルダに残すと処理対象に混入するので注意
