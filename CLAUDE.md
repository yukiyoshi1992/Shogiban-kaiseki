# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this project is

A tool that converts a sequence of smartphone photos (one photo per move of a shogi board) into a KIF-format game record. Board recognition uses a MobileNetV2 CNN (29-class classification per square: empty + 14 sente piece types + 14 gote piece types). Board alignment uses red-circle markers (auto-calibration); board orientation uses a blue-triangle marker.

All code lives under `train/src/`; the top-level `src/` and `.webaxs/` directories are empty/unused. There is no requirements.txt — dependencies observed in the code: `torch`, `torchvision`, `opencv-python` (`cv2`), `numpy`, `Pillow`, `python-shogi` (imported as `shogi`), `scikit-learn` (`train_model.py` only), `openpyxl` (for reading/writing the `docs/01 要件定義/*.xlsx` requirement docs), `streamlit` + `streamlit-image-coordinates` (installed 2026-06-18 for the planned simple operator UI — see `docs/handover.md` §7; no app code written yet).

For in-progress work and session-to-session continuity, see `docs/handover.md` (Japanese handover doc) — it is the authoritative source of truth for project status and should be consulted/updated alongside this file. (The older `docs/引き継ぎ資料.md` is archived at `docs/@old/引き継ぎ資料.md` as of 2026-06-19 — it's superseded by `docs/handover.md` and this file, not actively maintained.)

## Commands

All scripts are run directly with `python`, no build step. Paths in this repo are a Windows network share (`\\YukiYoshiNAS\Shogiban-kaiseki-tool\`); when invoked from a POSIX shell (bash tool) use `//YukiYoshiNAS/Shogiban-kaiseki-tool/...` instead of backslashes.

```bash
# Train the CNN (MobileNetV2 transfer learning) from labeled cell images
python train/src/train_model.py --cells "train/data/cells/" --out "train/models/" [--epochs 20] [--batch 16] [--val 0.2]

# Manual 4-corner calibration of a board photo
python train/src/calibrate.py --image <photo.jpg> --out <calib.json>

# Automatic calibration via red-circle markers
python train/src/auto_calibrate.py --image <photo.jpg> --out <calib.json>

# Batch manual calibration
python train/src/batch_calibrate.py --pattern <name> [--resume]

# Visually verify a calibration's grid alignment against photos
python train/src/check_calibration.py --calib <calib.json> --images <folder> --pattern <name>

# Detect blue-triangle orientation marker
python train/src/detect_triangle.py --image <photo.jpg>

# Debug: show 81-square recognition result for one image
python train/src/predict_cell.py --image <photo.jpg> --calib <calib.json> --model "train/models/"

# Label training data from a known piece-placement pattern (one calib may cover many photos of the same pattern)
python train/src/label_placement.py --images <folder> --calibs <calib_folder> --patterns-json train/src/placement_patterns.json --shift-json train/src/shift_patterns.json --out "train/data/cells/"

# Label training data from a KIF + game photos (reconstructs the correct board at each move and cross-checks against model recognition)
python train/src/label_from_kif.py --kif <game.kif> --images <folder> --calib <calib.json> --model "train/models/" --out "train/data/cells/" [--pattern <filename_prefix>] [--max-diff-accept 2] [--dry-run]

# Visually mass-review labeled cells before training
python train/src/check_labels.py --cells "train/data/cells/" [--samples N]

# Batch move-detection / KIF generation from a folder of sequential photos (testing/offline)
python train/src/detect_move.py --images <folder> --calib <calib.json> --model "train/models/" --out <output.kif>

# Production: watch a folder and generate KIF in real time as photos arrive
python train/src/run_realtime.py --watch "runtime/input/" --model "train/models/" --out "runtime/result/" [--idle-timeout 600] [--poll-interval 5]

# Audit per-frame, per-cell recognition accuracy against KIF ground truth (no move-matching cascade; every frame judged independently)
python train/src/audit_recognition.py --kif <game.kif> --images <folder> --calib <calib.json> --model "train/models/" [--force-direction right|left|up|down] [--out-pkl <results.pkl>]
```

There is no automated test suite; verification is done via `check_calibration.py`, `predict_cell.py`, `check_labels.py`, and by running `detect_move.py`/`run_realtime.py` against known games and comparing the resulting KIF to the ground truth.

## Architecture

### Coordinate system (must not be changed without updating every consumer)
- `row=0` is the top (9th file/筋), `row=8` is the bottom (1st file)
- `col=0` is the left (sente's first rank), `col=8` is the right (gote's side)
- `square = (8 - col) * 9 + row` — this is the mapping used everywhere code converts between the grid representation and `python-shogi`'s `Square` indices (see `rc_to_square`/`square_to_rc` in `label_from_kif.py` and the equivalent logic in `detect_move.py`).
- Training data orientation baseline: sente on the left, board shot landscape, sente pieces point right (▶), gote pieces point left (◀).

### The single most important invariant: rotate the image once, nothing else
`detect_move.py` and `run_realtime.py` determine orientation from the blue-triangle marker, then **rotate the source image itself** to match the landscape/sente-left baseline before any other processing. Calibration is then computed (or re-applied) against that already-rotated image. Grid coordinates and calibration matrices are never themselves rotated/transformed — only the raw image is. (An earlier version of `detect_move.py` had a "triple rotation" bug — rotating the image, the calib coordinates, *and* the grid labels — which silently broke recognition. Do not reintroduce per-orientation coordinate or grid transforms; the fix is documented in `docs/@old/引き継ぎ資料.md` §4-1.)

Blue-triangle apex direction → required rotation to reach the landscape baseline:
| apex direction | board orientation | rotation applied |
|---|---|---|
| right | sente left, landscape (baseline) | none |
| up | sente nearest camera, portrait | rotate 90° CCW |
| down | sente far from camera, portrait | rotate 90° CW |
| left | sente right, landscape | rotate 180° |

### Production flow (`run_realtime.py`) — corrected 2026-06-19 per user's authoritative process spec (`docs/chat.txt`)
1. Watch folder for new images.
2. On the first (move-0) image, try 3 automatic checks in order: (a) blue-triangle orientation detection, (b) red-circle calibration on the rotated image, (c) compare the recognized board against the standard starting position. **If any one of these three fails, immediately hand off to a human** who specifies the orientation and clicks the 4 board corners (`manual_calibration_flow()`, a self-contained port of `calibrate.py`'s mouse-click UI) — there is no "retake the photo and try auto-detection again" loop. Whatever the human produces is trusted unconditionally and the flow proceeds straight to "ready" (no re-verification afterward). This matches the user's explicit policy: automatic detection is just the first attempt; the instant any of the 3 checks errors, a human fixes it once, with no automated retry path in between.
   - **This replaced an earlier, incorrect design** (still described in some places in this repo's history) where a failed red-circle detection just printed "retake the photo" and waited for a new image, and the only "manual" option (`[r]`) merely let the operator pick a different rotation guess and re-ran the *same* automatic red-circle detection — there was no actual corner-click fallback. That gap was discovered as a side effect of the 001-raw room/lighting audit (see below): that room's red-circle markers don't reliably auto-detect in *any* of its 79 photos (confirmed: 0/79 pass strict detection), which would have produced an infinite "please retake the photo" loop in production with no real escape hatch.
   - Orientation detection from piece position (not just the blue triangle) was suggested as a nice-to-have by the user ("triangle, and if possible piece position too") but is **not yet implemented** — `detect_move.py`'s `detect_orientation_from_initial()` has the relevant logic (tries all 4 rotation+color-swap candidates against `INITIAL_BOARD_STD`) but isn't wired into `run_realtime.py`'s orientation step.
3. After move-0 is confirmed ready, the operator presses Enter (CLI stand-in for a future "対局開始" button in the planned Streamlit screen — see screen requirements below) before move-tracking begins.
4. Every subsequent image is rotated using the orientation locked in at move 0, calibration is applied, and recognition is compared against the **tracked `board` state** (not the previous photo) via `classify_frame`, brute-forcing legal continuations to find the move; this is then appended to the KIF.
5. **Not yet implemented**: 画面要件.xlsx's "認識エラー時の自動中止" policy (an unrecoverable recognition error should auto-abort the game like a manual abort, renaming the KIF to `【対局エラー中止】...`). `run_realtime.py` currently just logs `[認識ミス]` and keeps waiting for more photos on a `classify_frame` "error" status — it does not abort or rename any file. This is more naturally part of the Streamlit screen implementation (which owns the KIF filename state machine) than a CLI-only fix, so it's left as a tracked gap rather than patched here.

### Piece classes and the promotion/demotion constraint
29 classes total: `empty` + 14 sente + 14 gote (`fu, kyo, kei, gin, kin, kaku, hi, ou, tokin, nari_kyo, nari_kei, nari_gin, uma, ryu`). Promoted pieces share their physical token with the unpromoted piece, so the two share a hard count cap when building/validating a placement pattern: lance-family (kyo+nari_kyo) ≤4, knight-family ≤4, silver-family ≤4, gold ≤4, bishop-family (kaku+uma) ≤2, rook-family (hi+ryu) ≤2, king ≤2, pawn-family (fu+tokin) ≤18 — and per-side (sente-only or gote-only) bishop/rook/king/uma/ryu are capped at 1 each. Any new placement-pattern definition (in `placement_patterns.json`/`shift_patterns.json`) must respect these caps or the labeled data will be physically impossible.

### label_placement.py: validate new pattern data before trusting it
When a new entry is added to `placement_patterns.json` or `shift_patterns.json`, `label_placement.py` will silently mislabel cells as `empty` for any symbol it doesn't recognize or any structure it doesn't expect — it does not fail loudly. Two concrete cases already hit this:
- The king can be written as either `王` or `玉` depending on who placed the physical piece; `SYMBOL_TO_LABEL` must contain both (`"S王"`/`"S玉"` → `sente_ou`, `"G王"`/`"G玉"` → `gote_ou`) or king squares silently become `empty`.
- `shift_patterns.json` entries come in two shapes: a flat 9-element list (one row of pieces, placed at `target_row`) for older patterns, and a dict `{"rows": N, "row0": [...], "row1": [...]}` for newer ones (`shift_all_S/G`, `shift_nari_S/G`) that photograph multiple board rows shifted together in one shot — `row{k}` is placed at `target_row + k`. `shift_pattern_to_label_grid()` must branch on `isinstance(row_def, dict)`; treating the dict as a flat iterable silently iterates over its keys instead of piece symbols and mislabels the entire row as `empty`.

Before trusting a label_placement.py run on a newly-added pattern, scan for unrecognized symbols across every pattern (compare every symbol in `placement_patterns.json`/`shift_patterns.json` against `SYMBOL_TO_LABEL.keys()`) rather than relying on the `[WARNING]` lines in console output — console output on this Windows setup is cp932-encoded and can be cut off/garbled when captured through a redirected file or background task buffer, which makes it easy to miss a warning that occurred earlier in a long batch run.

A third case (found 2026-06-18, visually): unlike a wrong/unrecognized symbol, a **wrong row count in a pattern definition produces no warning at all** — `label_placement.py` has no way to know the table's row layout doesn't match the photo. `pattern11` in `placement_patterns.json` had a spurious extra blank separator row (an editing mistake — the photo only has one blank row between the two `と` rows, not a blank row before *every* piece group like other patterns in the same batch), which silently shifted every row from there on by one: real 香/桂 cells got labeled `empty`, real 銀/金 cells got labeled 香/桂, real 王/角/飛 cells got labeled 銀/金, and real *empty* cells got labeled 王/角/飛 (`sente_ou`/`gote_ou`/etc.). This is only catchable by warping a sample photo with its calib, overlaying row/col indices (see the diagnostic technique below), and comparing row-by-row against the table — not by anything label_placement.py prints. When adding a new pattern, render one annotated/warped sample and manually diff it against the table before trusting any of its output, especially when patterns in the same batch don't all share the same blank-row convention.

Diagnostic snippet for verifying a pattern/calib pair's row alignment (used to find the pattern11 bug):
```python
import cv2
warped, cell_px, grid_size = warp_image(img, calib)  # or extract_cells() from label_placement.py
for r in range(grid_size):
    for c in range(grid_size):
        cv2.putText(warped, f'{r},{c}', (c*cell_px+3, r*cell_px+15), cv2.FONT_HERSHEY_SIMPLEX, 0.4, (0,0,255), 1)
# save and view warped, compare row-by-row against the pattern table
```

### Calibration file convention
Calibration JSONs (`*_calib.json`) hold a `perspective_matrix`, `grid_size` (9), and `cell_px` (100), and are looked up by exact image stem (`{image_stem}_calib.json`) first. `label_placement.py`'s `find_calib()` falls back to a shared pattern-name calib (e.g. `pattern10a_calib.json`) when no per-image calib exists — this supports the "one calibration shared across many photos of the same fixed-camera pattern" shooting style used for production-room data (see `train/src/本番部屋_calib/`). Calib folders are organized by data batch (`追加学習_calib/`, `本番部屋_calib/`, `対局v2_calib/`, `対局_calib/`) — don't assume a single calib applies globally.

### Visual data review must cover every source batch, not just the recently-added one
When asked to visually verify `cells/` labels, it's easy to only sample the batch you were just working on and miss contamination elsewhere. `cells/` filenames carry a source prefix that identifies which batch produced them: `001`/`002` (対局v2), `対局` (old game data), `data1`–`data8` (old `data1`-style + `学習データ（最終場面画像＋対局kif）` endgame extraction), `pattern1`–`pattern11` (both placement-pattern batches), and `shift_*` (`shift_all/nari/baryu/kahigyoku/mix1/mix2/narifull`, each `_S`/`_G` and `_row{N}` suffixed). A 2026-06-18 review only checked `pattern9`–`11` and `shift_all/nari` (the batch just modified) and reported "no issues found" — `pattern1`–`8` and all of `data1`–`8` and the other `shift_*` patterns were silently never looked at. Before declaring a review complete, group `cells/<label>/*.jpg` by source prefix and confirm every prefix that exists for that label actually appears in the sample, not just a random draw that happens to be dominated by one or two batches.

### komadai (piece-stand) corner red dots are intentionally unused
Some training photos show red dots not just at the board's 4 corners but also on a small wooden block (駒台/piece stand) elsewhere in frame. Both `auto_calibrate.py` (`BOARD_RADIUS_RATIO_MIN/MAX`, `MIN_CIRCULARITY`) and `run_realtime.py`'s copy of `detect_red_circles`/`select_board_corners` deliberately filter circles by radius specifically so the board's (intentionally larger) red dots are picked and the komadai's smaller ones are excluded as noise. The komadai dots are not a calibration input anywhere — they can be physically removed from the prop without affecting any code.

### Model training takes hours on this CPU-only setup
`train_model.py` has no GPU available here (`torch.cuda.is_available()` is False), and unfreezes the full MobileNetV2 backbone for fine-tuning after epoch 10 (`if epoch == 9: ... param.requires_grad = True`), which roughly triples per-epoch time from there. A 20-epoch run on the current ~33k-image `cells/` took **~11h40m** wall-clock (epochs 1–10 ~30–38 min each, epochs 11–20 ~45–57 min each). `print()` output is fully OS-buffered when the process is backgrounded/redirected on this Windows setup — nothing appears in the log file until the process exits, so don't expect to tail progress; instead poll `train/models/best_model.pth`'s mtime (saved every time validation accuracy improves, not every epoch) or just wait for the background-task completion notification. `train/models/` (unlike `train/data/`) is **not** gitignored — `best_model.pth`/`model_meta.json` are tracked in git, so the previous model is always recoverable from git history. Still, before retraining it's convenient to also copy the current `train/models/{best_model.pth,model_meta.json}` to an untracked dated folder (e.g. `train/models_backup_YYYYMMDD/`) for a fast local rollback without git commands, and commit the newly trained weights once validated.

### Japanese-path / encoding handling
- Image I/O must go through `cv2.imdecode(np.fromfile(path, dtype=np.uint8), ...)` / `cv2.imencode(...)[1].tofile(path)` instead of `cv2.imread`/`cv2.imwrite`, because the latter don't handle non-ASCII (Japanese) paths on Windows.
- Console/log output is sometimes cp932-encoded; mojibake in captured stdout (e.g. background task logs) usually just needs re-decoding, not re-running.
- Rotated copies of source images may get written back into the same folder as `*_rot.jpg` during processing — don't let these leak into a later batch run as if they were new source photos.

- `001 ※画像が90度回転して入ってきている場合のパターン/` (the **raw**, never-used-for-training copy of the 001 game — distinct from `001 ※001の画像を正しい方向に90度回転加工済のデータ/`, which is the *same* KIF/game but a manually pre-rotated copy that did contribute a few cells previously): **55/78 moves correct, 23 errors**. Triangle auto-detected as `up` (rotate 90° CCW) — confirmed correct by visually checking the warped move-0 board against the standard initial position. Errors cluster in two places: 3 isolated failures right at the start (moves 1, 3, 4 — an early single-frame recognition glitch that self-corrects), then a long clean run (moves 5–52), then a dense failure block from move 53 onward (53–58, 60–63, 65–70, 72–75) that the diff-based algorithm cannot self-recover from once it starts (a failed frame freezes the tracked board state, so the next comparison must explain *two* real moves at once, which usually has no legal match either — failures cascade). This is a genuine model/lighting accuracy gap specific to this room's data, not a pipeline bug — consistent with the already-documented poor recognition for the 001 game's room/lighting (see below). In a real production run (`run_realtime.py`), this game would have triggered the "recognition error → auto-abort" path at the very first failure, not run to completion.
- `auto_calibrate.py`'s red-circle detector failed (only found 2/4 corners) on the rotated 001 move-0 image — two corners had circularity scores (0.32–0.34) below `MIN_CIRCULARITY` (0.45), likely from partial occlusion/glare, even though their radius was in-range. Worked around by manually reading the 4 circle centers from the unfiltered contour list (`detect_red_circles`'s pre-filter output) and building the calib directly via `auto_calibrate.compute_grid()`/`save_json()` — `auto_calibrate.py` itself was not modified. If this recurs often, the fix would be loosening `MIN_CIRCULARITY` or detecting circles independent of the strict radius+circularity AND, but a single one-off manual override was simplest here.
- Found and fixed a **KIF-output bug** in `detect_move.py`'s `moves_to_kif()`: the move-source square in parentheses (e.g. `(27)`) was being built from `sq_name_to_ja()`'s *Japanese* (full-width file digit + kanji rank) representation reverse-engineered back into a number, producing a mixed full-width-file + half-width-rank string (e.g. `(４1)`) instead of the correct all-half-width `(41)`. This isn't just cosmetic: `shogi.KIF.Parser` re-parsing such a file silently stops at the first move it can't match (no exception raised) — confirmed on the 002 output, where only 24/111 moves parsed back before silent truncation. Fixed by computing the source square's file/rank as plain ASCII digits directly from the USI square name instead of round-tripping through the kanji string. Verified fix: re-parsed 002's regenerated KIF matches the 111-move ground truth exactly. Any KIF file produced by `detect_move.py` *before* this fix should be treated as suspect/unverified if it was meant to be re-parsed by another tool.

### Root cause of the 001 raw-folder cascading failures (2026-06-19): human piece-straightening mid-game, not a model/calib bug
Drilled into the move-53 failure cluster from the retest above. Comparing the two source photos directly (`IMG_20260616_150958.jpg` → `IMG_20260616_151012.jpg`, the move-53 transition): the first photo has a hand (holding a mouse) in frame casting a shadow over the sente side, with several sente back-rank pieces (銀/金/王 area) visibly tilted; the second photo has the hand gone, no shadow, and those same pieces visibly straightened. **Nothing was actually "moved" as a shogi move between these two frames — a human reached in to fix tilted pieces, mid-game, which is exactly the not-yet-handled scenario tracked as "駒のずれ直し対応" (piece-realignment handling) in `docs/handover.md`.** The diff-based algorithm in `detect_move.py`/`run_realtime.py` has no concept of "the board changed but no legal move explains it, because a human nudged a piece" — it tries to interpret the pixel diff as a move, fails to find a legal one, and (per `detect_changes`/`infer_move`) freezes the board state and lets the corruption propagate into the next comparison, which is why one straightening event triggered a long unrecoverable error run (53 through 75) rather than a single isolated failure.
Separately (and not yet fully root-caused): comparing the model's per-frame recognition against the ground-truth KIF-replayed board for this same folder showed ~30 of 81 cells already persistently wrong as early as move 51 (i.e. before the move-53 incident), all at confidence 1.0. This suggests piece-realignment/lighting disruptions like the one above may have happened more than once earlier in this particular game's photo session, with effects that persist (since nobody resets a piece's pixel-level position back to its "trained" appearance) — this is circumstantial, not confirmed against further photos, but is consistent with the same root cause rather than a separate calibration or model defect.

### 駒のずれ直し対応 (2026-06-19): classify_frame replaces photo-to-photo diff with board-anchored move search
The move-53 finding above (a human straightening tilted pieces mid-game, no real move) is the concrete case for the previously-tracked "駒のずれ直し対応" item. Root cause: `detect_move.py`/`run_realtime.py` compared **the previous photo's recognition to the current photo's recognition**, requiring the delta to match a legal move; any non-move visual change (realignment, lighting) broke that match, and the old code's failure handling froze the corrupted state forward, so one bad frame cascaded into many.

Fix (in both `detect_move.py` and `run_realtime.py`, kept duplicated per `run_realtime.py`'s existing self-contained-file convention): replaced `detect_changes`+`infer_move`+`find_legal_move`/`find_legal` with `classify_frame(board, recognized)`, which compares **the authoritative `board` state (converted to a label grid via the new `board_to_label_grid()`, ported from `label_from_kif.py`) to the new photo**, then brute-forces every legal continuation from `board` (depth 1, and if nothing matches well, depth 2 — i.e. up to two plies ahead) looking for the sequence whose resulting grid has the smallest `diff_count()` against the photo:
- Exact match (`diff0==0`) → `"nochange"` (photo is identical to the tracked board; do not advance).
- A *uniquely* best move/move-pair with diff ≤ `MOVE_DIFF_THRESHOLD` (currently 2) → `"move"`, push it (or both, if a depth-2 catch-up was needed) and append to the KIF.
- Anything else (no candidate within threshold, or a tie between multiple equally-good candidates) → `"error"` (same fallback behavior as before: log it, do not advance).

**Important: do not reintroduce a "small-diff therefore no real move happened" shortcut.** An earlier draft of this fix treated any `diff0` below a small threshold (e.g. ≤2, not just 0) as automatic `"nochange"`. This is unsafe and caused a real regression during testing: a frame where the model failed to detect a real move on one square while *also* hallucinating an unrelated 2-square change elsewhere has the same small `diff0` as genuine noise, but is not noise — swallowing it as a no-op permanently desyncs `board` from the true game for the rest of the sequence (no future frame can ever resolve it, since the missing ply's identity is gone). `nochange` must stay restricted to an exact pixel-perfect match against the tracked board; anything else must go through the legal-move search and, if it doesn't resolve cleanly, fall through to `"error"` — guessing wrong is worse than aborting (matches the existing 画面要件.xlsx No.6 policy).

Verified: `002/` still gets 111/111 with the new logic (no regression; KIF re-parses to an exact match against ground truth). `detect_changes` is kept in `detect_move.py` only as a `--preview` visualization helper (no longer drives the move decision); `infer_move`/`find_legal_move` (and `run_realtime.py`'s `prev_labels`/`label_to_piece`/`PROMOTED_TO_BASE`/equivalents) were dead code after the change and were deleted rather than left unused.

### 001 raw moves 1/3/4 (`IMG_20260616_150603.jpg` etc.): confirmed CNN misclassification, not a regression, not a coordinate bug
While testing the `classify_frame` fix against `001 ※画像が90度回転して入ってきている場合のパターン/`, moves 1/3/4 still failed (now as `"error"`/ambiguous rather than a wrong guess). Investigated whether this was a rotation/coordinate bug introduced by the manually-built calib (`train/test_runs/001raw_calib.json`, made earlier this session after `auto_calibrate.py` only found 2/4 red circles — see above): re-ran the same early frames through a **second, independent calibration path** (the user's own manually-pre-rotated copy of this exact game, `学習データ（対局画像＋対局kif）3/001_180fix/`, combined with the pre-existing `対局v2_calib/001_calib.json`) and got the **identical** per-cell recognition result. This rules out a calibration/rotation bug — the discrepancy is in the model's prediction itself, not the geometry pipeline.

What the model actually outputs for `IMG_20260616_150603.jpg`: a clean, single 2-cell change at row1 (file8, the bishop's file) — but **no change at row7 (file2, the rook's file)**, where the real first move (`２六歩`, KIF move 1) physically already happened by that point (confirmed by the user looking at the photo directly: the pawn in front of the rook has already advanced one rank). So for this one photo, the model both (a) failed to detect the real change on file2, and (b) hallucinated an unrelated, plausible-looking single-pawn-push change on file8 that had not actually happened yet. Confirmed via file timestamps that this exact misreading was already present in the very first test run of the session (`train/test_runs/001raw_detect_log.txt`, generated **before** `detect_move.py` was touched today) — `predict_board()` itself was not modified by this session's `classify_frame` work, so this is not a regression from the fix.

This room/session's photos contributed only 3 cells total to `cells/` during the 3rd retrain (see the `label_from_kif.py` section above), so the 99.94% overall validation accuracy doesn't say much about this specific room's recognition floor. Final counts after the fix: `001 ※画像が90度回転して入ってきている場合のパターン/` accepts only 3/78 moves (down from the old algorithm's 55/78) — this is **not a regression in quality**, it's the new algorithm correctly refusing to guess on ambiguous frames that the old algorithm may have resolved by silently picking whichever legal candidate came first, without checking for ties. Given this session's evidence (an isolated bad frame at the very start, a separate human piece-straightening incident around move 53, and a third batch of persistent low-confidence-pattern mismatches found mid-game), **this specific room/session's data has a real recognition ceiling that no amount of move-matching-algorithm improvement can fully overcome** — the next useful signal is testing against the new, never-touched held-out test data (`学習用の撮影データ/テストデータ（対局画像＋対局KIF）/`, see `docs/handover.md`) to see whether this is specific to this one room/session or a broader pattern.

### audit_recognition.py: frame-vs-KIF-ground-truth comparison, independent of move-matching cascade
`detect_move.py`'s `classify_frame` freezes the tracked `board` on any unresolved frame, so every subsequent frame's diff is computed against a state that may already be wrong — this makes it impossible to tell whether a later frame is "really" misrecognized or just inheriting an earlier failure's corruption (this is exactly the 001-raw cascade described above). `train/src/audit_recognition.py` (added 2026-06-19) sidesteps this: it reuses `label_from_kif.py`'s `load_kif_boards()` to replay the KIF into one ground-truth grid per move index, then compares **each photo's recognition directly against the ground-truth grid at that same index** (1:1, no search, no cascade) — every frame is judged independently. Useful both for diagnosing a known-bad room/session (see the 001-raw findings below) and for evaluating accuracy on new held-out test data once it has a calib.

### 001-raw (`学習データ（対局画像＋対局kif）3/001 ※画像が90度回転して入ってきている場合のパターン/`): RESOLVED (2026-06-19) — root cause was an orientation bug, not a model/calibration accuracy limit
**Final result: 79/79 frames perfect (0/6399 cells wrong) and `detect_move.py` reconstructs all 78/78 moves with the generated KIF an exact match to the ground-truth KIF.** The root cause was simply that the blue-triangle auto-detector returned `up` (→ rotate 90° CCW) for this photo set, but the *correct* rotation was `down` (→ rotate 90° CW) — 180° off from what auto-detection picked. Once a human visually confirmed the correct orientation and re-did the 4-corner calibration on the correctly-rotated image (`train/test_runs/001raw_calib_v2.json`, built via `calibrate.py`'s manual click flow), every single one of the elaborate findings below (model can't distinguish kin/ou, confidence is uninformative, calibration crop misalignment, etc.) disappeared. **None of those theories were real** — they were all artifacts of comparing a 180°-rotated board's recognition against the correctly-oriented ground truth, which (per the shogi board's point-symmetric structure) produces exactly the "point-symmetric pairs with color flipped" error signature that was investigated at length below.

**Process lesson (the actual takeaway to retain)**: this entire detour happened because earlier in the session, "two independently-built calibrations agreeing with each other" was (wrongly) treated as proof the geometry pipeline was correct — but it only proved the two calibrations weren't *grossly* different, not that the orientation feeding into them was right. The error was only caught when the user happened to look at the actual rotated image being calibrated and immediately recognized "sente is on the right, that's backwards" — something no amount of Claude-side pixel/diff analysis caught or could reliably catch (an 180°-rotated shogi board is *designed* to look locally plausible, since real games often have locally-symmetric-looking formations). **Whenever orientation/rotation is in question, get a human to look at the actual oriented image and confirm sente-left before trusting any downstream analysis — don't try to infer orientation correctness from recognition statistics alone.** This is now reflected in `run_realtime.py`'s production flow (any orientation/calibration/initial-position check failure routes straight to a human, no automated retry/self-diagnosis).

The original (incorrect) multi-day investigation — including the "model can't distinguish certain piece pairs," "confidence is uninformative," and "calibration corner marker is degraded" theories — is preserved in `docs/@old/001生データ認識誤り分析.md` as a worked example of this failure mode, with a correction notice at the top. Not worth re-reading for this game's data specifically, but worth remembering the pattern: symmetric-looking error signatures across point-symmetric board squares are a signature of an orientation bug, not a model weakness, and should prompt re-checking orientation by eye before anything else.
